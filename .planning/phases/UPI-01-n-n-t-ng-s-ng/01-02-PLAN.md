  <name>Task 1: Schema, Prisma config, and the offline initial migration</name>
  <files>prisma/schema.prisma, prisma.config.ts, prisma/migrations/0_init/migration.sql</files>
  <action>
Write `prisma/schema.prisma` with a generator block using provider `prisma-client` (NOT the legacy
`prisma-client-js`) and output `../src/generated/prisma`. The modern generator emits TypeScript
that the Next build typechecks natively; the legacy one emits JS plus declaration files and is
being phased out. `output` is mandatory in Prisma 7.

The datasource block declares `provider = "postgresql"` and NOTHING else. In Prisma 7 the
datasource has no `url` and no `directUrl` field — both moved to `prisma.config.ts`. Also do NOT
add `previewFeatures = ["driverAdapters"]`; driver adapters are generally available in 7 and the
flag is gone.

Define exactly five models, per RESEARCH.md §5. Four are Auth.js adapter models whose field names
are dictated by the adapter, not by us:

- `User`: `id` as a cuid primary key, optional `name`, optional `email` with a unique constraint,
  optional `emailVerified` timestamp, optional `image`, `createdAt` defaulting to now, and
  relations to `accounts` and `sessions`. The unique on `email` is required — the adapter looks
  users up by it.
- `Account`: cuid id, `userId`, `type`, `provider`, `providerAccountId`, the OAuth token columns,
  a cascade-delete relation to `User`, and a compound unique on `[provider, providerAccountId]`
  which the adapter queries by. The OAuth token column names MUST be snake_case
  (`refresh_token`, `access_token`, `expires_at`, `token_type`, `scope`, `id_token`,
  `session_state`) because the adapter forwards the raw OAuth response object straight into a
  create call. Renaming them to camelCase produces an unknown-argument error at first login only
  — never at build time — which is the worst possible time to discover it.
- `Session`: cuid id, `sessionToken` with a unique constraint, `userId`, `expires`, and a
  cascade-delete relation to `User`. Cascade matters for the seed's revocation behavior in Task 3.
- `VerificationToken`: `identifier`, `token`, `expires`, compound unique on `[identifier, token]`.
  Unused by a Google-only setup, but the adapter's type requires the model to exist.

Do NOT add an `Authenticator` model — that is for WebAuthn passkeys and is not used here.

The fifth model is ours: `Allowlist`, with `email` as the String primary key (always lowercase),
an optional `label` for a pre-login display hint, and `invitedAt` defaulting to now.

Write `prisma.config.ts` at the project root: import `dotenv/config` for side effects, then
export a config declaring `schema` as `prisma/schema.prisma`, `migrations.path` as
`prisma/migrations`, `migrations.seed` as `tsx prisma/seed.ts`, and `datasource.url` read from
`DATABASE_URL_UNPOOLED` via the config helper. Seed configuration belongs under `migrations` in
Prisma 7 — the old `package.json` `prisma.seed` block is a Prisma 6 mechanism and is silently
ignored now.

The datasource here is deliberately the UNPOOLED connection: schema changes cannot be executed
across a connection pooler. The pooled string is for the running app only, and is wired in Task 2.

Finally, generate the initial migration WITHOUT a database. No Neon project exists yet (that is a
human step in plan 06), and the first Vercel deploy will run `prisma migrate deploy`, which needs
a migration directory to apply. Create `prisma/migrations/0_init/`, then produce its
`migration.sql` by diffing an empty datamodel against the schema file and emitting a script.
Note that the diff command still loads `prisma.config.ts` and therefore still requires
`DATABASE_URL_UNPOOLED` to be set even though it touches no database — set a syntactically valid
placeholder Postgres URL in the environment for that one command. Confirm the emitted SQL
contains create-table statements for all five tables.

  <name>Task 2: Prisma client singleton over the pooled Neon adapter</name>
  <files>src/lib/db.ts</files>
  <action>
Create the project's single database entry point. Every later phase imports `prisma` from here;
nothing else constructs a client.

Read the pooled connection string from `DATABASE_URL` into a local constant and throw an explicit
Error naming the missing variable if it is absent. Use a real guard, not a non-null assertion:
the assertion trips Biome's no-non-null-assertion rule, and more importantly an undefined
connection string otherwise surfaces later as a confusing driver-level error instead of a clear
startup failure.

Construct the client by passing a Neon driver adapter built over that connection string. Using
the pooled string through the adapter is what satisfies INFRA-06 — serverless functions scale out
horizontally, and without pooling, concurrent function instances exhaust the database's direct
connection limit.

Wrap the instance in the standard development singleton: stash it on a `globalThis` property and
reuse it when present, assigning only when not in production. Without this guard, `next dev`
leaks a fresh Neon client on every hot reload until the dev server runs out of connections.

Import `PrismaClient` from `@/generated/prisma/client` — note the `/client` suffix, which is where
the modern generator emits it. Importing from `@/generated/prisma` will not resolve.

<task type="auto" tdd="true">
  <name>Task 3: Allowlist parser with tests, and the authoritative seed script</name>
  <files>src/lib/allowlist.ts, src/lib/allowlist.test.ts, prisma/seed.ts</files>
  <behavior>
`parseAllowlist` is a pure function over the raw env string. Write these tests first, then the
implementation:
- Parses a comma-separated list into one entry per email.
- Lowercases every email. An entry written with capitals must come back lowercased — a seeded
  mixed-case address would never match the lowercased lookup performed at sign-in, silently
  locking out a real member. This is the single highest-value assertion in the file.
- Parses an optional `:label` suffix into `label`, and yields `null` when the suffix is absent.
- Trims surrounding whitespace around both entries and labels.
- Ignores empty segments produced by trailing or doubled commas.
- Throws when the raw value is undefined, and throws when it parses to zero entries. Seeding an
  empty allowlist would lock every member out of the app, so this must fail loudly rather than
  quietly write nothing.
  </behavior>
  <action>
Extract the parser into `src/lib/allowlist.ts` rather than leaving it inside the seed script.
`prisma/seed.ts` sits outside `src/`, which makes it awkward to import from a test; putting the
pure logic in `src/lib/` makes it directly testable and lets the seed import it. Export
`parseAllowlist` returning entries of `{ email, label }`, with the behavior fixed in the block
above. Input format is `email[:label]`, comma-separated.

Write `src/lib/allowlist.test.ts` covering every listed behavior before implementing.

Then write `prisma/seed.ts` as an AUTHORITATIVE sync, not a one-way upsert. This is a locked user
decision and it is the heart of the plan. Rationale worth preserving in a comment at the top of
the file: if the seed only ever added rows, then the environment variable and the database table
would drift into two different answers to "who is a member" — the precise failure mode that
killed this project's predecessor. Removing a member must be one edit plus one command.

The script resolves its connection from `DATABASE_URL_UNPOOLED`, falling back to `DATABASE_URL`,
throwing if neither is set. It builds its own Prisma client over the Neon adapter — it runs as a
standalone `tsx` process outside the Next runtime, so it does not use the app singleton.

It then performs three steps, in this order:

1. Upsert every parsed entry, keyed on the email primary key: update the `label` on conflict,
   create otherwise. Keeping `invitedAt` out of the update branch preserves the original
   invitation timestamp across re-runs.
2. Delete every `Allowlist` row whose email is NOT among the parsed emails.
3. Revoke access for anyone just removed: delete the `Session` rows belonging to users whose
   email is no longer in the allowlist. This step is mandatory and non-obvious — the sign-in
   callback runs only at login, never on subsequent requests, so a removed member otherwise keeps
   a valid session for its full lifetime. Deleting the allowlist row alone does not evict anyone.
   Compare emails case-insensitively here, since `User.email` comes from the OAuth provider and
   is not normalized by us.

Report counts for all three operations on stdout so a human running `pnpm seed` can see what
actually changed rather than assuming.

The script must exit non-zero on failure and disconnect the client when finished.
  </action>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| operator env var → database | `ALLOWLIST_EMAILS` decides who may use the app at all |
| serverless functions → Postgres | Many concurrent instances share a finite connection budget |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-01 | Elevation of Privilege | `prisma/seed.ts` | high | mitigate | Seed deletes allowlist rows absent from the env var AND deletes the removed users' `Session` rows. Verification greps for `deleteMany` and session handling so an upsert-only regression fails the gate |
| T-02-02 | Spoofing | `Allowlist.email` casing | medium | mitigate | Parser lowercases unconditionally; a dedicated unit test asserts it. Sign-in lookup (plan 04) lowercases symmetrically |
| T-02-03 | Denial of Service | Neon connection exhaustion | high | mitigate | Pooled `DATABASE_URL` through `PrismaNeon` for runtime; unpooled reserved for DDL; dev singleton prevents hot-reload client leaks |
| T-02-04 | Tampering | Schema drift between code and production | medium | mitigate | Migration files are committed and applied by `migrate deploy` during build. Convention established: never run `prisma db push` against production, since that creates tables without migration history and makes every later deploy fail |
| T-02-05 | Information Disclosure | Connection strings | critical | mitigate | Read from env only; never literal in source; `.env*` git-ignored by plan 01 |
</threat_model>
