Build the static app shell and the design token system it rests on.

Purpose: INFRA-07 requires the interface to appear while Neon's compute is still resuming. The
mechanism is a layout that performs no data access at all — the shell is therefore prerenderable

of consistent colour, type, spacing and dark mode are the actual payoff.

<task type="auto">
  <name>Task 1: Design tokens in globals.css</name>
  <files>src/app/globals.css</files>
  <action>
Replace the scaffold's one-line `globals.css` with the complete token system transcribed verbatim
from UI-SPEC.md section "The Tailwind v4 `@theme` Block". Keep `@import "tailwindcss";` as the
first line. Transcribe every block in the order the spec gives them, with its explanatory
comments intact.

The structure, and why each part is shaped the way it is:

- An `@theme inline` block for `--font-sans`. The `inline` variant is required specifically
  because this token references another variable (the font variable that `next/font` generates).
  Without `inline` the utility resolves to the variable reference itself and can fall back
  unexpectedly.
- A plain `@theme` block for everything else: the five type tokens with their paired
  line-height and font-weight values, the two font weights, the spacing base, three radii, three
  shadows, the light-mode semantic colours, the easing token, the skeleton animation token, and
  the nested skeleton keyframes.
- A dark-mode block that reassigns the SAME semantic colour tokens inside a
  prefers-color-scheme media query on `:root`. It must be a plain media block, NOT nested inside
  `@theme` — `@theme` must stay top level. Because only token values change and no component
  references a raw colour, dark mode costs zero component edits.
- A `:root` block holding `color-scheme: light dark` plus the safe-area and shell-geometry
  variables. These stay plain CSS variables rather than theme tokens because they are dynamic
  values, not utility generators.
- A `@layer base` block: body background/colour/font, the 16px minimum font-size rule for form
  controls, the focus-visible outline, and the reduced-motion override.
- A `@layer components` block defining the `.money` class with tabular lining numerals.
- A prefers-contrast-more block lifting muted text and borders.

Three details that look like style choices but are load-bearing:

The input font-size floor exists because iOS Safari zooms the viewport whenever a focused form
control is under 16px. The rule is the reason the viewport config can avoid disabling pinch-zoom,
which would be an accessibility failure. It is a floor, not a default — do not override it later.

`--shell-tabbar-height` is composed as the tab bar's content height plus the bottom safe-area
inset. `--shell-tabbar-content` is 0px today; Phase 3 changes that single value to mount the tab
bar and every screen's scroll bottom corrects at once. Consumers use `--shell-tabbar-height`
alone and must never add the inset a second time, which would leave a dead gap under every screen.

The skeleton animation is an opacity pulse rather than a translating gradient sweep. Opacity is
compositor-only; a moving gradient forces repaints, which is the wrong trade on a low-end Android
phone over 4G — the exact device this app targets.

  <action>
Rewrite the scaffolded layout as the static shell described in UI-SPEC.md section "App Shell".

Load Inter through `next/font/google` with subsets `['latin', 'vietnamese']`, `display: 'swap'`,
the CSS variable `--font-inter`, and the optical-size axis enabled. The `vietnamese` subset is not

Export `viewport` with device width, initial scale 1, `viewportFit: 'cover'`, and the two
theme-colour entries for light and dark. `viewportFit: 'cover'` is required: without it the
safe-area inset environment variables all evaluate to zero and the shell geometry silently
collapses to a non-notched layout. Do NOT set a maximum scale or disable user scaling — the 16px
input floor from Task 1 already solves the zoom-on-focus problem, and disabling pinch-zoom is a
WCAG failure.

The component itself renders `<html lang="vi">` carrying the font variable class, then a body
with the surface and ink token classes, then a column flex container holding:
- A `<header>` with the `Upper-I` wordmark in accent colour and an empty right-hand slot sized to
  the minimum touch target, reserved for the Phase 3 avatar.
- A `<main>` holding `children`, with horizontal gutter padding and bottom padding of the tab bar
  height token.
- A comment marking where Phase 3 mounts the bottom tab bar.

`lang="vi"` matters beyond correctness: it drives screen-reader pronunciation and browser
hyphenation. The scaffold writes `lang="en"`.

Compute the header's height as the content height PLUS the top safe-area inset, with the inset
applied as top padding. This ordering is the whole point: if the header were given a fixed height
with the inset merely padded inside it, the inset would eat the content box — on a phone whose
top inset exceeds the content height, the usable header height computes negative and the header
collapses. The bar's total height must grow by its inset, never absorb it. This rule binds every
later bar in the project.

The hard constraint for this file: it must contain no `await`, no `auth()` call, and no database
access of any kind. The session is read inside the page, not the layout. If the layout awaited
anything, the entire shell would block on Neon's cold start and INFRA-07 would be violated by
construction — the requirement would be unreachable no matter what the pages do.

<task type="auto">
  <name>Task 3: The three UI primitives</name>
  <files>src/components/ui/button.tsx, src/components/ui/card.tsx, src/components/ui/skeleton.tsx, src/components/ui/submit-button.tsx</files>
  <action>
Three plain function components, per UI-SPEC.md "Component Inventory". No class-variance-authority,
no tailwind-merge, no clsx — the variant surface here is two values, and a dependency to express
that is not worth its weight.

`Button`: renders a native `<button>`, never a clickable div. The native element brings a tab
stop, Enter and Space activation, and an implicit role for free; a div needs three separate
additions to approximate that and each is a chance to get it wrong. Accepts `variant` of
`'primary'` or `'bordered'` and spreads the remaining native button props. Minimum height is the
44px touch target (use 48px in practice for comfort), width is full, radius is the control token,
text is the body token at semibold.

The `bordered` variant uses the raised surface with a strong border; `primary` uses the accent
background with the on-accent foreground. Implement `primary` even though Phase 1 never uses it —
both buttons in this phase are `bordered` — so Phase 3's save action has it ready.

When `pending` is true, set `disabled` and `aria-busy`, and render the caller-supplied pending
label. The button must not change width between states, or the layout shifts under the user's
thumb mid-tap. Disabling on first submit also prevents a double-tap on flaky mobile data from
firing a second request.

**Specify where `pending` comes from, because the obvious answer does not work here.** Both
buttons in this phase submit a form bound to a server action, so there is no client-side handler
to flip a piece of state — the component cannot know on its own that a submission is in flight.
The value comes from React's form-status hook, which reports the pending state of the enclosing
form.

That hook only works in a client component, and only when the component calling it is a **child**
of the `<form>` rather than the component that renders the form. So split the pieces:

- `Button` stays a plain presentational component. It takes `pending` as a prop and renders
  accordingly. It is not a client component and knows nothing about forms, which keeps it usable
  in static contexts and in any later phase that drives it some other way.
- A thin client wrapper — a submit button — calls the form-status hook and passes the result down
  to `Button`. This wrapper carries the client directive. It is the only client component in the
  phase.
- The pages keep rendering a server-side `<form>` bound to the action, with the wrapper inside it.

The ordering constraint is the part most likely to be gotten wrong: putting the hook in the same
component that renders the `<form>` always reports not-pending, because the hook reads the form
context from above it. The result is a button that silently never shows feedback — it looks
correct in code review and fails only when a user taps it on a slow connection, which is exactly
when the feedback mattered.

Keep the client boundary this small deliberately. Making a page or the layout a client component
to get a pending state would pull the session-rendering path into the client and undermine the
static shell the phase is built around.

Never add `outline: none` or any focus-suppressing class; the global focus-visible ring from
Task 1 applies and its 2px offset already clears the control radius.

`Card`: a `<div>` with the raised surface, the border token, the card radius, the card shadow,
and internal padding. Children only.

`Skeleton`: a `<div>` taking a `className` for sizing and carrying the `skeleton` class whose
animation, 150ms delay, zero starting opacity and forwards fill mode come from Task 1's CSS. The
delay matters: content that arrives in under ~150ms should never flash a placeholder, because a
skeleton that appears and vanishes inside a frame or two reads as a glitch rather than as loading.

Document the sizing contract in a comment, because it is the part callers get wrong: callers size
the skeleton in `em` inside a wrapper carrying the type token of the text being replaced — never
with a fixed height utility. A display-sized line of text is 41.6px tall, which is not a multiple
of 4 and therefore inexpressible in the spacing scale; the nearest utilities are 1.6px short and
2.4px over, and either one guarantees the layout jump the skeleton exists to prevent. Sizing in
`em` resolves against the wrapper's own font size, so the box is exact and stays exact if the type
token is ever retuned.
  </action>
