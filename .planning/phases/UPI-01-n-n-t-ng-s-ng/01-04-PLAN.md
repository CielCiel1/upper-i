<objective>
Wire Google sign-in with a database-backed session and a database allowlist gate, and guard every
protected route.

Purpose: The allowlist is this app's only access control, so it has to hold at two independent
points — at login, where it decides whether an account is ever created, and on every request,
where the route guard decides whether a session is still valid. This plan builds both and proves
each one mechanically.

Output: Working one-tap Google sign-in restricted to invited members, a 30-day persistent session,
a sign-out action usable from any screen, and a route guard verified present in the build output.
</objective>

  <action>
Create `src/auth.ts` configuring Auth.js v5 with the Prisma adapter over the shared client from
`@/lib/db`, the Google provider, and a database session strategy.

Session config: strategy `database`, max age 30 days, update age 1 day. The 30-day window is what
delivers AUTH-03 — the user opens the app the next day and is still signed in. Database sessions
rather than JWT is a locked decision, and the reason is revocation: a JWT stays valid until it
expires no matter what the database says, so removing a member could not take effect until their
token aged out. A database session can be revoked by deleting one row.

Record one correction in a comment next to the session config, because the project's own context
document states it slightly too strongly: a database session makes revocation *possible and
immediate*, but not *automatic*. The sign-in callback runs only on the OAuth callback path, not
on session reads, so the allowlist table is not consulted per request. Revocation happens because
the seed script deletes the `Session` row, not because the session re-checks the allowlist. Plan
02 implements that deletion; this comment exists so a future reader does not assume a protection
that is not there.

Pages config: `signIn` points at `/dang-nhap`, and `error` points at `/dang-nhap` as well, so
genuine OAuth failures return to the sign-in screen where the UI-SPEC's error copy lives. Do not
point `error` at the rejection page — allowlist refusal is deliberately handled as its own
redirect below, and conflating the two would show "not invited" for unrelated network failures.

The `signIn` callback is the allowlist gate. In order: reject anything whose provider is not
Google; reject when the profile carries no email or the email is not verified by Google (an
unverified address can be attacker-controlled and must never be matched against the allowlist);
lowercase the email and look it up in the `Allowlist` table by primary key.

On a match, allow the sign-in. On no match, return a redirect **string** to the rejection route
carrying the attempted email as a URL-encoded query parameter. Returning a string here is a
supported, typed behavior of this callback — it redirects the user and, critically, it does so
from the same point in the flow as returning false, which is *before* any row is written.

That last point is the mechanism behind AUTH-02 and deserves a comment in the file. Auth.js runs
this callback inside its authorization step, which executes strictly before the step that creates
users, links accounts, and creates sessions. A refusal here therefore writes nothing at all —
there is no account to clean up afterwards, and no partially-created user. This guarantee comes
from library internals rather than from our code, so the phase verifies it against the live
database rather than trusting it.

**The string-return path writes no rows, exactly like returning false.** This is worth stating
because it is the obvious worry about carrying data out of the callback. Internally, the
authorization step converts a returned string into a redirect and hands it back to its caller,
which returns immediately on receiving one — before reaching the registration step on the very
next line. Both the refusal path and the redirect path exit above that line, so neither can create
a user, link an account, or issue a session. The live row-count check in the final plan covers
this empirically rather than relying on the reading.

The reason for the redirect-with-email rather than a bare refusal: the UI-SPEC's rejection screen
must name the email that was used, because the overwhelmingly common real cause is tapping the
wrong one of several Google accounts signed in on the phone. But a refused user has no session,
so the page cannot look the email up afterwards — nothing was persisted. Passing it through the
redirect is what makes the specified screen buildable. Include a marker parameter in that
redirect identifying it as an access-denied outcome, alongside the encoded email: plan 05's page
uses it to reject direct navigation, and the two parameters together are that page's entry
contract.

**Accepted tradeoff, recorded deliberately: this puts an email address in a URL.** That means it
can appear in browser history on a shared phone, in hosting access logs, and in the `Referer`
header of any subsequent outbound request from that page. The alternatives were weighed:

- Omitting the email satisfies privacy but breaks the specified screen, which exists precisely to
  let someone recognise that they used the wrong account. That is the screen's entire job.
- A short-lived signed token or a server-side lookup keyed by a one-time id avoids the URL, but
  both require persisting state for a user the system has just decided not to persist anything
  for — which reintroduces exactly the write that AUTH-02 forbids.

It is accepted because the exposed value is the address the person just chose to sign in with on
their own device, disclosed back only to themselves; it is not a secret, not a credential, and
grants nothing. Two mitigations are required rather than optional: the rejection page must carry
a referrer policy that prevents the URL being forwarded to third parties, and the page must not
load any third-party resource. Phase 1 loads no third-party resources at all, so the second holds
by construction — but state it, because a later phase adding an analytics script to the global
layout would silently break it.

The `session` callback copies `user.id` onto `session.user.id`, so later phases have the stable
internal identifier.

No `declare module` augmentation is needed to *read* `session.user.id` — the installed version
already types it, and the augmentation block shown in most tutorials is obsolete here. Verified:
`const id: string | undefined = s?.user?.id` compiles clean under strict.

But note the exact shape, because it is the thing that will bite in the callback: on the library's
types both `user` and `id` are **optional**, so the property is `string | undefined` and `user`
itself may be undefined. A bare `session.user.id = user.id` does not compile under strict — it
produces "possibly undefined" on the container and a `string | undefined` to `string` mismatch on
the assignment. Write the callback so it narrows first: confirm `session.user` exists before
assigning, and return the session unchanged otherwise. The same applies at every read site, which
is why the page uses optional chaining and falls back when the name is absent.

This matters beyond type-checking: `noUncheckedIndexedAccess` and strict mode are on precisely so
these absences are surfaced at compile time rather than rendering `undefined` into a greeting.

Create the route handler at `src/app/api/auth/[...nextauth]/route.ts` re-exporting `GET` and
`POST` from the config's handlers.

Finally, extend `src/lib/allowlist.ts` with a small exported helper that normalizes an email for
comparison (trim and lowercase), and use it in the callback. Add tests to the existing
`src/lib/allowlist.test.ts` asserting it lowercases, trims, and that a mixed-case address
normalizes to the same value the seed stores. This closes the loop on the casing hazard from plan
02: seeding and lookup must normalize identically or a real member is silently locked out.

  <name>Task 2: Route guard at src/proxy.ts</name>
  <files>src/proxy.ts</files>
  <action>
Create the per-request route guard by re-exporting the auth handler from `@/auth` under the name
`proxy`, and export a `config` whose matcher excludes the paths that must stay reachable to a
signed-out visitor: the auth API, the sign-in page, the rejection page, the web manifest, icons,
Next's static and image endpoints, and the favicon. Everything else requires a session.

Two things about this file are easy to get wrong and both are serious.

First, the filename. Next.js 16 renamed this convention from `middleware` to `proxy`. The old name
still functions but is deprecated, and the two must never both exist. Most tutorials still show
the old one.

Second — and this is the single most dangerous mistake available anywhere in this phase — the
file must live at `src/proxy.ts`, beside the `app/` directory, NOT at the repository root. The
convention is "project root, or inside `src` if applicable", and this project uses a `src`
directory, so `src/` is the correct level. Placed at the repository root the file is silently
ignored: the build still succeeds, no warning is printed, no test fails, and every protected
route is simply public. It fails open, and it passes every check except one.

That one check is the build output, which lists the proxy as a route-table entry only when the
file is actually wired. Treat its presence as a hard gate, not a nice-to-have — it is the only
available evidence that the guard exists at all. The verification below asserts it, and plan 05
asserts it again against the full build.

Note that this guard runs on the Node runtime, which is why Prisma and database sessions work
inside it directly, with none of the edge-runtime splitting that older Next.js versions forced.

One limitation to record in a comment, because it shapes Phase 2: this guard does not protect
server actions. Server actions must each re-check `auth()` themselves. Phase 1 has only the
sign-out action, where it hardly matters, but the pattern is established now so that Phase 2's
money-mutating actions inherit it.

`signInWithGoogle` starts the Google OAuth flow with a redirect target of `/`.
`signOutAction` ends the session with a redirect target of `/dang-nhap`.

Both are deliberately server actions invoked from a plain form rather than click handlers on a
client component. The reason is the target environment: a form posting to a server action works
before JavaScript has hydrated, which matters on the flaky mobile connection this app is used on

statically prerenderable.

for this particular action, but it establishes the pattern that the route guard does not cover
server actions, and Phase 2's actions will mutate money.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Google OAuth callback → app | Externally-originated identity assertion crosses here |
| Anonymous HTTP request → protected routes | The route guard is the only thing between the two |
| Query string → rejection page render | Attacker-controllable display text |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-04-01 | Elevation of Privilege | `src/proxy.ts` placement | critical | mitigate | File must sit at `src/proxy.ts`; verification asserts the file location, the absence of a root-level copy, the absence of any `middleware.ts`, and (in plan 05) the proxy entry in the build route table. This is the phase's only fail-open defect |
| T-04-02 | Spoofing | Unverified Google email | high | mitigate | `signIn` rejects any profile lacking a Google-verified email before the allowlist lookup, so an unverified attacker-controlled address can never match an invited one |
| T-04-03 | Spoofing | Non-member account creation | critical | mitigate | Allowlist lookup in `signIn`, which Auth.js runs before user/account/session creation. Verified live against the database in plan 06 by asserting the row count is unchanged after a refused attempt |
| T-04-04 | Elevation of Privilege | Removed member retains session | high | mitigate | Database session strategy plus the plan 02 seed deleting `Session` rows for removed members. The sign-in callback alone does not re-run per request |
