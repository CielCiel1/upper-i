that the token system renders correctly on a real phone. The structural work is where the session

**The build-breaking constraint that shapes every file here.** The project is configured with
cached components enabled, which makes any access to cookies, headers, or search params outside a
Suspense boundary a hard build failure rather than a warning. Both the session read and the
rejection page's query-string read are affected. The fix is not a workaround — wrapping the
dynamic read in Suspense is what turns the route into a partial prerender, and that *is* the
INFRA-07 deliverable. Structure the pages this way by design, not in reaction to an error.

Build the sign-in screen per UI-SPEC.md "Screen 1". It must be fully static — no session read, no
database access, nothing to await. This is the first thing a user on mobile data sees, so it has
to paint immediately.

Layout is a single centred column, max width small, vertically centred in the viewport. Contents
in order: the wordmark `Upper-I` in display type and accent colour; the tagline
`Chia tiền nhóm, số dư luôn đúng.` in body type and soft ink, constrained to a comfortable
measure and centred; the Google sign-in button; and the footnote
`Chỉ thành viên trong nhóm mới đăng nhập được.` in caption type and muted ink.

The footnote is doing real work and should not be trimmed as redundant: it sets expectations
before the tap, so that a refusal reads as confirmation of something already stated rather than
as a surprise failure.

`src/components/google-mark.tsx` renders the Google "G" as inline SVG at the official four
colours. Mark it `aria-hidden` and non-focusable — it is decorative, and the button's text
already provides the accessible name. Inline SVG avoids pulling in an icon library for one mark.

`src/components/sign-in-button.tsx` is a form bound to the `signInWithGoogle` server action,
containing a real submit button. Use the shared `Button` primitive in its `bordered` variant. Render it
through the `SubmitButton` wrapper from plan 03 rather than `Button` directly — that wrapper is
what supplies the pending state from the enclosing form, and it must sit inside the `<form>`.

The button is deliberately NOT accent-filled even though it is the primary action. Prominence
comes from being the only element on the screen; Google's branding expects a neutral button
carrying the official mark, and a teal-filled Google button looks off-brand in a place where
trust matters most.

Label is `Đăng nhập với Google`. While submitting, the label becomes `Đang chuyển tới Google…`
and the button is disabled with a busy state. Keep the width fixed across the swap so the layout
does not shift under the thumb, and the disabled state prevents a double-tap on a slow connection
from starting two OAuth round-trips.

Because this is a form posting to a server action, it works before hydration — the control is live
as soon as the HTML arrives.

  <action>
Two screens, both structured around a Suspense boundary.

**`src/components/sign-out-button.tsx`** — a form bound to the `signOutAction` server action
containing a `bordered` Button labelled `Đăng xuất`, with the pending label `Đang đăng xuất…`.
Use the `SubmitButton` wrapper here too, for the same reason.
Accept an optional label prop so the rejection screen can reuse the component with different
wording. Keeping this as a form with a server action rather than a session-aware client component
means the control carries no session data and therefore never forces its container to render
dynamically.

**`src/app/page.tsx`** — the authenticated home, per UI-SPEC.md "Screen 3".

The page component itself is static. It renders a Suspense boundary around a separate async child
component that performs the session read, plus the static status card and the sign-out button
outside that boundary.

The async child calls `auth()`, then renders the greeting `Chào {name}` in display type, and the
email beneath it in caption type and muted ink. Fall back to the Google-provided name when a
display name is unset. Both lines are needed and prove different things: the name proves the
session resolved and the database round-trip succeeded, while the email proves *which* identity
authenticated — without it, a successful sign-in by the wrong Google account is indistinguishable
from a correct one, which matters when testing the allowlist.

The Suspense fallback holds two skeletons sized per the spec's sizing contract: each sits inside a
wrapper carrying the type token of the text it stands in for, and is sized in `em` against that
token rather than with a fixed height utility. The greeting's line box is not a multiple of the
spacing scale, so no height utility can express it exactly and every available one guarantees a
visible jump when the real text lands.

Outside the boundary, static and immediate: a `Card` containing
`Nhóm đã sẵn sàng. Tính năng ghi chi tiêu sẽ có ở bản cập nhật tiếp theo.`, then the sign-out
button, which satisfies AUTH-06 for this screen.

This page must contain no balance, no money, no navigation, no tab bar — Phase 1 ships no
transaction surface of any kind.

**`src/app/chua-duoc-moi/page.tsx`** — the rejection screen, per UI-SPEC.md "Screen 2".

The attempted email arrives as a query parameter, set by the sign-in callback in plan 04. It must
be read inside a Suspense boundary. Note that search params resolve as a promise here and must be
awaited.

Treat that value as untrusted input, because anyone can craft the URL. Before display: trim it,
cap its length to something reasonable for an email, and render it only if it matches a basic
email shape; otherwise render the sentence without the email rather than echoing arbitrary text.
It is interpolated as React text content, never as markup. This is display-only data — it is
never used for a lookup or any decision.

Because the URL of this specific page carries an email address, set a referrer policy on it that
prevents the full URL being sent onward in the `Referer` header. Export the page's metadata with a
no-referrer policy. The risk it closes is narrow but real: any outbound request initiated from
this page would otherwise disclose the address to a third party. Phase 1 loads nothing
third-party, so the exposure is currently zero — the policy is here so that a later phase adding a
script or an embedded resource to the shared layout cannot silently open it.

**Guard against direct navigation.** This route is deliberately excluded from the route guard so a
signed-out, refused visitor can actually reach it — which means anyone can also type the URL, or
land on it with a hand-written query string. Without a check, the page renders a "you are not
invited" message to people who never attempted to sign in, and renders whatever email a visitor
puts in the URL back to themselves.

Inside the same Suspense boundary that reads the query string, require evidence that the visit
followed a real refusal: the redirect issued by the sign-in callback carries a marker parameter
identifying it as an access-denied outcome, so check for it and redirect to `/dang-nhap` when it
is absent. The sign-in callback in plan 04 must therefore include that marker in the redirect URL
it builds, alongside the encoded email — treat the pair as the page's entry contract.

This is not an authentication boundary and should not be mistaken for one: it carries no secret
and anyone can forge the parameter. Its job is to stop accidental and casual access to a confusing
page, which is the realistic failure, and to keep the reflected-email surface off a URL that is
otherwise trivially discoverable.

Copy, verbatim: heading `Email này chưa được mời`; then
`Tài khoản {email} chưa có trong danh sách thành viên của nhóm.` with the email wrapped in a
`<strong>` for emphasis; then
`Nếu bạn nghĩ đây là nhầm lẫn, nhắn cho người quản lý nhóm để được thêm vào.`

The action button reuses the sign-out component with the label `Dùng tài khoản khác`. The label
deliberately names the user's goal rather than the mechanism: telling someone to "sign out" of an
account they were just told is not welcome is confusing, whereas "use a different account" is what
they actually want to do. A refused user has no session, so the underlying sign-out is a no-op
server-side — its real effect is clearing the Google account selection and returning them to
sign-in.

Tone constraints that are easy to violate by reflex: no red, no warning icon, no error styling.
Nothing went wrong — the system worked correctly and the person simply has not been invited yet.
Use ordinary ink colours on a plain card. The heading is the page's single `<h1>`.

<task type="auto">
  <name>Task 3: Prove the build output — prerendering and the route guard</name>
  <files>src/app/page.tsx, src/app/chua-duoc-moi/page.tsx</files>
  <action>
Run a full production build and assert its route table, then fix any page that fails the shape.

This task exists because two of the phase's most important properties are invisible to every other
kind of check, and both are readable in the build output.

First, the route guard. A guard file placed at the wrong level is silently ignored: the build still
succeeds and every protected route becomes public. The build output lists the proxy as a route-table
entry only when it is genuinely wired, so that line is the only available evidence that the guard
exists at all. Assert it.

Second, prerendering. Each app route must be marked static or partially prerendered; none may be
fully dynamic. A fully dynamic marker on an app route means its shell waits on the server before
painting, which is exactly the failure INFRA-07 exists to prevent. The auth API route is expected
to be dynamic — that is correct for an API endpoint and is the one exclusion.

**Match dynamic ROUTES specifically, by anchoring on the dynamic marker followed by a path
separator.** Two near-miss formulations both look right and both are wrong:

- Matching the dynamic marker anywhere on the line also matches the proxy's own route-table entry,
  which legitimately carries that marker and is not an app route. That makes a correct build fail.
- Delimiting the route table by scanning to the first blank line does not work either: in the
  verified build output there is no blank line between the last route and the proxy entry, so the
  proxy line falls inside the scanned range regardless.

Anchoring on marker-then-slash avoids both, because the proxy entry is followed by a letter rather
than a path. Excluding the API route must likewise be anchored to the path, not matched loosely
against the whole line.

Before trusting this gate, run it against three fixtures: the verified-good output from the
research document, a copy with the home route forced dynamic, and a copy with the proxy line
deleted. It must pass the first and fail the other two. A gate that has only ever been run against
a passing build is not known to work — it is only known not to have complained.

**The `DATABASE_URL` placeholder below must use a host containing `-pooler`.** This is a hard
coupling with plan 02, not a cosmetic choice. That plan makes `src/lib/db.ts` throw at module load
when `DATABASE_URL` is not a pooled endpoint (INFRA-06). Prerendering `/` imports the page, which
imports the auth config, which imports the database client — so a non-pooled placeholder throws
during prerender and fails this build, which would take down the only gate that proves INFRA-07
and the route guard. A plain `localhost` placeholder is exactly that failure.

Note the asymmetry and keep it: `DATABASE_URL` is pooled-shaped, `DATABASE_URL_UNPOOLED` is not.
They must not both be given the same host, or a swap of the two would stop being detectable.

Neither value connects to anything — nothing in this build opens a socket. They exist only to
satisfy the two modules that read and validate them at import time.

Build locally with placeholder values for the database URLs. The build runs the project's build
script, which generates the Prisma client and attempts to apply migrations; migration application
will not succeed without a reachable database, so for this check run the generate and build steps
directly rather than the full script. Set both database URL variables to syntactically valid
placeholders — the config loader resolves them eagerly and fails the build if either is absent,
with an error mentioning neither the database nor deployment, which is easy to misread.

If a route comes back fully dynamic, the cause is a cookie, header or search-param read sitting
outside a Suspense boundary. Move that read into a child component inside the boundary rather than
opting the route out of prerendering — opting out would trade away the requirement to silence the
symptom.

Capture the route table in the plan summary so the next phase inherits a known-good baseline.
