<interface_contract>
The checklist is written in **Vietnamese**, numbered, with per-step time estimates, stating
exactly what to click and what to copy where. Code identifiers, environment variable names,
commands and URLs stay in their original form inside the Vietnamese prose.

**The ordering is forced by a circular dependency and must not be rearranged.** Google needs the
production URL to register a redirect URI, while the app needs Google's credentials to work. The
resolution is that the hosting provider assigns the production domain at project import — before
any build has succeeded — so the order runs: create the database, import the project and read the
assigned domain, configure Google against that domain, paste the environment variables, then
trigger the real deploy. The first deploy, attempted at import time with no environment variables
present, is EXPECTED TO FAIL. The checklist must say so plainly at that step, because an
unexplained red build is exactly the kind of thing that reads as "I broke it" and stalls the
sitting.
</interface_contract>

Write `01-SETUP-CHECKLIST.md` in Vietnamese as a numbered list. Each step states where to go, what
to click, what to copy, where to paste it, and an estimated duration. Open with the total estimate
and a one-paragraph explanation of why the order is what it is, so the reader understands the
circular-dependency resolution rather than experiencing it as arbitrary.

Steps, in this exact order:

1. Create the Neon project. Region must be Singapore (`ap-southeast-1`) — it has to match the
   hosting function region already committed in `vercel.json`, so that queries do not cross
   regions on every request. ~3 min.
2. Copy both connection strings from the Connect panel: with pooling enabled that is
   `DATABASE_URL`, with pooling disabled that is `DATABASE_URL_UNPOOLED`. Paste both into a local
   `.env.local`. Explain the split: the pooled string is for the running app, where many
   concurrent function instances would otherwise exhaust the connection limit; the direct string
   is for schema changes, which cannot be executed through a pooler. ~2 min.
3. Import the GitHub repository into Vercel. The framework is detected automatically. Deploy once
   — **state explicitly that this first build fails, that this is expected, and that it is not a
   mistake**, because no environment variables exist yet. Then read and write down the production
   domain the project was assigned. Note that if the preferred project name is already taken
   globally, the assigned domain will differ, so the actual value from the dashboard must be used
   in step 7 rather than an assumed one. ~4 min.
4. Create the Google Cloud project. ~2 min.
5. Configure the OAuth consent screen: External, with only the three identity scopes, and leave
   the publishing status as Testing. Explain the tradeoff being accepted: Testing mode means
   manually keeping the Google test-user list in sync with the database allowlist, and in exchange
   it provides a second independent gate at no cost. ~8 min.
6. Add every member's Gmail address as a test user. State that this list must match
   `ALLOWLIST_EMAILS` exactly, and explain how a mismatch presents, because the symptom tells you
   which list is wrong: an address missing from Google's test users is blocked by Google before
   ever reaching the app, while an address missing from the database allowlist reaches the app and
   lands on the "chưa được mời" screen. ~3 min.
7. Create the OAuth client ID for a web application. Authorized JavaScript origins are the local
   development URL and the production domain from step 3. Authorized redirect URIs are those same
   two origins each followed by the auth callback path. Copy the client ID and secret. Warn that
   redirect URI mismatches are character-exact — scheme, trailing slash, and the full callback
   path all matter — and that preview deployment URLs are randomly generated and therefore cannot
   be registered, so sign-in will not work on previews by design. ~5 min.
8. Generate the auth secret locally with `npx auth secret` and copy the value. ~1 min.
9. Paste all six variables into the Vercel project settings, ticking Production, Preview and
   Development for each: both database URLs, the auth secret, the Google client ID and secret,
   and the trust-host flag. Call out specifically that `DATABASE_URL_UNPOOLED` is required at
   BUILD time, not just at runtime, because the Prisma config resolves it eagerly — if it is
   missing the build fails with a message that mentions neither the database nor deployment and
   is easy to misdiagnose. ~5 min.
10. Trigger a fresh deploy with the build cache disabled. The build generates the client, applies
    the migration, and builds the app. ~3 min.
11. Seed the allowlist: put the member list in `.env.local` as `ALLOWLIST_EMAILS` in
    `email[:label]` comma-separated form, point `DATABASE_URL_UNPOOLED` at the production
    database, and run `pnpm seed`. Note that this must come after step 10, since the tables do not
    exist until the migration has run. ~3 min.
12. Confirm zero cost: check that the hosting plan is Hobby and the database plan is Free, and
    that no payment card is attached to either. Note that Google OAuth in Testing mode is free.
    ~3 min.
13. End-to-end check on a phone over mobile data — detailed as its own checkpoint task below.

Add a short closing section on member management, since it is the operation the group will
actually perform repeatedly: adding or removing a member means editing `ALLOWLIST_EMAILS` and
running `pnpm seed`, plus mirroring the change in the Google test-user list. State plainly that
the seed is authoritative — it removes rows that are no longer listed and deletes the removed
person's sessions, which is what makes removal take effect immediately rather than whenever their
session would have expired.

Then update `README.md` with: prerequisites (Node 22.12 or newer, pnpm via corepack), local setup
(copy `.env.example` to `.env.local`, fill it, install, seed, run), the available scripts and what
each does, and that same member add/remove runbook. Include one convention as a standing rule:
never run a schema push against the production database — always generate a migration — because a
push creates tables without migration history and every subsequent deploy then fails to apply
migrations against it.
