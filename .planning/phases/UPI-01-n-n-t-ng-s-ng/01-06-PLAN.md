Steps, in this exact order:

1. Create the Neon project. Region must be Singapore (`ap-southeast-1`) — it has to match the
   hosting function region already committed in `vercel.json`, so that queries do not cross
   regions on every request. ~3 min.
2. Copy both connection strings from the Connect panel: with pooling enabled that is
   `DATABASE_URL`, with pooling disabled that is `DATABASE_URL_UNPOOLED`. Paste both into a local
   `.env.local`. Explain the split: the pooled string is for the running app, where many
   concurrent function instances would otherwise exhaust the connection limit; the direct string
   is for schema changes, which cannot be executed through a pooler.

   **Include an explicit visual confirmation step here, because swapping these two is silent.**
   Tell the reader to check that the host in `DATABASE_URL` contains `-pooler` and that the host

   app still builds, still deploys, and still works for one person testing it — it fails later,
   under real concurrent use, as intermittent connection errors that look like a Neon outage
   rather than a configuration mistake. The app also refuses to start when `DATABASE_URL` is not
   pooled, so a swap surfaces as a clear startup error rather than a mystery. ~2 min.
3. Import the GitHub repository into Vercel. The framework is detected automatically. Deploy once

  <how-to-verify>
Work through `.planning/phases/UPI-01-n-n-t-ng-s-ng/01-SETUP-CHECKLIST.md` from step 1 to step 12
in one sitting (~35–45 minutes). Do not reorder the steps — step 3 produces the domain that step 7
needs, and step 7 produces the credentials that step 9 needs.

Then run these checks and report the result of each:

1. **Sign-in works (AUTH-01).** Open the production URL on your phone over mobile data. Tap
   `Đăng nhập với Google`, pick an allowlisted account. Expected: the home screen shows
   `Chào {your name}` and your email beneath it.

2. **The interface renders correctly (INFRA-07 and the token system).** On that same screen:
   the header and background appear immediately, before the greeting does. Vietnamese tone marks
   render cleanly with no clipping. Content clears the notch and the home-indicator area. Switch
   the phone to dark mode — the whole screen re-skins and stays readable.

3. **A non-member is refused, and creates nothing (AUTH-02).** This check needs a before-and-after
   comparison. A single reading taken afterwards proves nothing, because there is no reference
   number to compare it against — "the counts look about right" is not a verification.

   **Step 3a — capture the baseline FIRST, before attempting anything.** In the Neon SQL editor:
   ```sql
   SELECT (SELECT count(*) FROM "User")    AS users,
          (SELECT count(*) FROM "Account") AS accounts,
          (SELECT count(*) FROM "Session") AS sessions;
   ```
   Write the three numbers down. Do not skip this and reconstruct them later from memory.

   **Step 3b — attempt the refused sign-in.** Sign out, then sign in with a Google account that is
   NOT in the allowlist but IS registered as a Google test user. (It must be a test user, or
   Google blocks it on its own side and the app's gate is never exercised — that would be a
   different test passing for the wrong reason.) Expected: the `Email này chưa được mời` screen,
   showing the email you just used.

   **Step 3c — re-run the exact same query and compare.** All three numbers must be **identical**
   to the baseline. `users` and `accounts` unchanged proves no account was created. `sessions`
   unchanged proves no session was issued. If any number increased, AUTH-02 has failed and the
   phase does not ship — report the before/after pair rather than approving.

   **This is the single most important check in the phase.** The guarantee that a refusal writes no
   rows comes from the authentication library's internal ordering, not from our own code, so it is
   verified against the database rather than trusted. A future dependency bump could reorder it
   silently, which is exactly why the check is a count comparison and not an inspection of our
   source.

4. **Adding a member needs no redeploy.** Add an email to `ALLOWLIST_EMAILS`, add the same address
   as a Google test user, run `pnpm seed`. That person signs in immediately, with no deploy.

5. **Removal takes effect immediately, without destroying history.** Remove that email again and
   re-run `pnpm seed`. On their device, reload the app. Expected: they are signed out.

   Then confirm all three outcomes in the SQL editor — the third is the one most likely to be
   skipped, and is the one that protects Phase 2:
   ```sql
   SELECT (SELECT count(*) FROM "Allowlist" WHERE email = 'removed@example.com') AS allowlist_rows,
          (SELECT count(*) FROM "Session" s JOIN "User" u ON u.id = s."userId"
             WHERE lower(u.email) = 'removed@example.com')                       AS live_sessions,
          (SELECT count(*) FROM "User" WHERE lower(email) = 'removed@example.com') AS user_rows;
   ```
   Expected: `allowlist_rows` 0, `live_sessions` 0, and **`user_rows` still 1**. The user row must
   survive. It is the permanent foreign-key target for every ledger row Phase 2 will write, so
   removing someone's access must never delete the person that historical expense rows point at.
   If `user_rows` came back 0, the seed is deleting users and must be fixed before Phase 2 starts.

6. **Push deploys automatically (INFRA-03, INFRA-04).** Make a trivial commit on the main branch
   and push. Expected: a deployment starts on its own, the build log shows the migration step
   running, and the live site serves the new build with no manual action.

7. **Session persists (AUTH-03).** Two parts, because the full requirement cannot be observed in
   one sitting and waiting a day is not a verification strategy.

   Immediately: fully close the app (not just background it) and reopen it. Expected: still signed
   in, no new login prompt. This proves the session cookie is persistent rather than a session
   cookie that dies with the browser process — which is the actual failure mode worth catching.

   Then confirm the stored expiry rather than waiting for it:
   ```sql
   SELECT expires, expires > now() + interval '29 days' AS has_full_window FROM "Session";
   ```
   `has_full_window` must be true, proving the 30-day lifetime was really applied rather than a
   library default of some shorter period. Re-opening the app the next day is still worth doing as
   a sanity check, but it is no longer what the requirement rests on.

8. **Sign-out works from every screen (AUTH-06).** Two screens carry a sign-out control and both
   must work, since the requirement is "from any screen" and only testing one proves half of it.

   On the authenticated home, tap `Đăng xuất`. Expected: back at the sign-in screen, and reopening
   the app does not restore the session. Confirm the row is gone, not merely the cookie:
   `SELECT count(*) FROM "Session";` must have decreased by one.

   Then on the rejection screen, tap `Dùng tài khoản khác`. Expected: it returns to the sign-in
   screen without error. (This one is a no-op server-side, since a refused user never had a
   session — what is being verified is that it does not error and does route correctly.)

9. **The bill is zero (INFRA-05).** Confirm the hosting plan reads Hobby, the database plan reads
   Free, and no payment card is attached to either account.
