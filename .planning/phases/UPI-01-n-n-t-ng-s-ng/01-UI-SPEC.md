# Phase 1 — UI Design Contract

> Visual and interaction contract. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope note:** Phase 1 ships three trivial screens. The real deliverable of this document is the
**design token system** that all 9 phases consume. Effort is weighted ~70% tokens / ~30% screens,
per the phase brief. Every value below was verified empirically — contrast ratios computed,
colour-blindness simulated, font tables parsed. Sources and measurements are shown inline so a
later phase can re-derive rather than re-litigate.

---

## Design System

| Property | Value |
|----------|-------|
| Tool | none (no shadcn) |
| Preset | not applicable |
| Component library | none — hand-rolled; Radix primitives deferred to Phase 3 (bottom sheet) |
| Icon library | none in Phase 1 — inline SVG. Deferred: `lucide-react` when Phase 3 needs a tab bar |
| Font | **Inter** (variable), subsets `latin` + `vietnamese`, via `next/font/google` |

### Why no shadcn

The shadcn gate was evaluated and **deliberately declined**. Reasons, in order of weight:

1. **shadcn's value is component scaffolding; Phase 1 has three screens and ~2 components.**
   A sign-in button, a message card, and a sign-out button. `npx shadcn init` would add
   `components.json`, `class-variance-authority`, `clsx`, `tailwind-merge`, and `tw-animate-css`
   to serve two buttons.
2. **shadcn presets ship an opinionated OKLCH palette built around a neutral + single primary.**
   This app's most important colour decision is the *owed/owe pair*, which no preset encodes.
   We would override the palette immediately, keeping only the plumbing.
3. **CONTEXT.md commits to Biome.** shadcn's generated components are Prettier/ESLint-shaped and
   produce lint churn on first `biome check`.
4. **It remains available later.** shadcn v4 reads `@theme` tokens. Because every token below is
   *semantic* (`--color-surface`, not `--color-stone-50`), a later `shadcn init` can be pointed at
   this theme without a repaint. This is a deferral, not a rejection.

**Revisit trigger:** Phase 3 (bottom sheet + tab bar) or Phase 5 (dialog for QR). If a focus-trapped
modal is needed, adopt Radix primitives directly rather than full shadcn.

## Font Decision — Inter, and why not Be Vietnam Pro

Both candidates were downloaded and their OpenType tables parsed directly (`fontTools`), not assumed.

| Check | Be Vietnam Pro | Inter | Why it matters |
|---|---|---|---|
| Vietnamese glyph coverage | ✅ complete | ✅ complete | Tested 25 stacked-diacritic glyphs (`ế ộ ữ ặ ỹ ẳ ồ …`) — zero missing in both |
| `U+20AB` ₫ dong sign | ✅ | ✅ | Every money string ends in it |
| Google Fonts `vietnamese` subset | ✅ | ✅ | Subset includes `U+1EA0-1EF9` + `U+20AB` |
| **`tnum` (tabular figures)** | ❌ **absent** | ✅ **present** | **Decisive** |
| Default digit widths | proportional | proportional | Neither is tabular without the feature |
| Variable font | ❌ static only (18 files) | ✅ `opsz 14–32`, `wght 100–900` | One file, any weight |
| Extra OT features | `ss01` | `ss01`, `cv01` | — |

**Be Vietnam Pro is rejected on `tnum`.** Its `GSUB` table has no `tabular-nums` feature, and its
digits are proportional (measured advance widths `[676, 385, 651, 660, 710, 660, 680, 594, 634, 680]`
— note `1` is 385 vs `4` at 710, a 1.84× difference). In a balance list, `111.000 ₫` would render
visibly narrower than `444.000 ₫`, and a column of amounts would not align. Applying Tailwind's
`tabular-nums` utility to this font emits `font-variant-numeric: tabular-nums`, which the font
**silently ignores**. That is the worst failure mode: the class is present, the code review passes,
and the digits still jitter.

This matters from Phase 4 onward (balance list), Phase 6 (settlement suggestions), and Phase 7
(monthly report columns). Choosing the font that cannot do it, in Phase 1, to discover the problem
in Phase 4, is exactly the kind of retrofit this phase exists to prevent.

**Inter** has `tnum` confirmed present, is a variable font (single network request covers 400 and
600), and has complete Vietnamese coverage. It is also the most widely-shipped UI typeface, so the
system fallback degrades gracefully.

### Font stack

System fallbacks are listed for the `font-display: swap` window and for the offline case. Every
fallback named below renders Vietnamese correctly on its platform:

```
Inter, -apple-system, BlinkMacSystemFont, "Segoe UI", Roboto,
"Helvetica Neue", Arial, "Noto Sans", sans-serif
```

- `-apple-system` → **SF Pro** (iOS/macOS): full Vietnamese, has tabular figures.
- `Roboto` (Android): full Vietnamese since Android 4.x, has tabular figures.
- `Segoe UI` (Windows): full Vietnamese.
- `Noto Sans`: explicit catch-all with guaranteed Vietnamese coverage.

**Do not** add `system-ui` as the first fallback — on some Android builds it resolves to a font
without complete Vietnamese tone-mark positioning.

### Loading

```ts
// app/layout.tsx
import { Inter } from 'next/font/google';

export const inter = Inter({
  subsets: ['latin', 'vietnamese'],   // 'vietnamese' is REQUIRED — omitting it drops ₫ and all tone marks
  display: 'swap',
  variable: '--font-inter',
  axes: ['opsz'],
});
```

`subsets: ['vietnamese']` is non-negotiable. Without it the `U+20AB` ₫ and the `U+1EA0-1EF9`
block fall through to the system font, producing mixed-typeface money strings.

## Vietnamese Line-Height — a measured constraint, not a preference

Vietnamese stacks a vowel diacritic *above* and a tone mark *below* the same glyph. The ink extents
of Inter's worst-case glyphs were measured from the font outlines (`BoundsPen`, 2048 upm):

| Glyph | Ink top | Ink bottom |
|---|---|---|
| `Ế` | **+1.105em** | 0.000em |
| `Ồ` | +1.105em | −0.010em |
| `Ộ` | +0.942em | −0.206em |
| `ặ` | +0.761em | **−0.206em** |
| `ỹ` | +0.745em | −0.208em |
| `g` (latin ref) | +0.553em | −0.216em |

**Worst-case ink span = 1.105 − (−0.216) = 1.321em.**

A line-height below ~1.32 risks ascender/descender collision between adjacent lines of Vietnamese
text, and in a clipping container (`overflow-hidden`, a common card pattern) the top of `Ế` is cut.

**Therefore `leading-tight` (1.25) is banned project-wide for Vietnamese body and heading text.**
Tailwind's default `leading-tight`/`leading-none` must never be applied to prose. The minimum is
**1.3**, and that only for short, controlled, single-line display text where a stacked-diacritic
capital is unlikely to be followed by a descender on the next line.

| Context | Line height | Rationale |
|---|---|---|
| Display / page title | **1.3** | Short, often single line. Above the 1.321 collision threshold only marginally — acceptable because adjacent-line collision needs *two* lines |
| Heading | **1.35** | Safely clears 1.321 |
| Body | **1.5** | Comfortable reading; well clear |
| Label / caption | **1.4** | Clears 1.321 with margin at small sizes |
| Money (tabular) | **1.2** | **Permitted exception** — digits and `₫` have no diacritics. Ink span of `0123456789₫` is ~0.73em. Applies only to elements containing *nothing but* a formatted amount |

## Spacing Scale

Tailwind v4 generates spacing dynamically from a single `--spacing` base rather than a fixed map.
The default base is `0.25rem` (4px) and **we keep it** — it already yields every multiple of 4
(`p-1`=4px … `p-16`=64px) with no configuration.

Declared values (all multiples of 4):

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px (`1`) | Icon gaps, inline padding |
| sm | 8px (`2`) | Compact element spacing, gap between toggle avatars |
| md | 16px (`4`) | **Default** element spacing, screen gutter |
| lg | 24px (`6`) | Section padding, card interior |
| xl | 32px (`8`) | Layout gaps |
| 2xl | 48px (`12`) | Major section breaks |
| 3xl | 64px (`16`) | Page-level spacing, empty-state vertical rhythm |

**Deviations from Tailwind v4 defaults:** none to the scale itself. We add two *named semantic*
tokens that are not spacing multiples, documented as exceptions below.

### Exceptions (justified)

| Exception | Value | Why it is not a multiple of 4 |
|---|---|---|
| `--size-touch-min` | **44px** | Apple HIG minimum touch target. 44 is not a multiple of 8 but is a hard platform constant. Used as `min-h`/`min-w` on every interactive element |
| `--shell-gutter` | `max(16px, env(safe-area-inset-left))` | Resolves to 16px on non-notched devices; larger in landscape on notched phones. Dynamic by nature |
| `--shell-safe-bottom` | `max(16px, env(safe-area-inset-bottom))` | Clears the iOS home indicator. Dynamic by nature |

44px is **larger** than the research minimum in one place by design: the UX doc specifies member
avatars in the exclude-row must be ≥44px with ≥8px gaps because a mis-tap silently changes who pays.
Phase 1 has no such control, but the token is declared now so Phase 3 does not invent its own.

## Typography

Font: **Inter**, weights **400 (regular)** and **600 (semibold)** — exactly two, per contract.
No 500, no 700. The variable font makes both free in bytes; the discipline is visual, not technical.

| Role | Size | Weight | Line Height | Tailwind |
|------|------|--------|-------------|----------|
| Display | 32px / 2rem | 600 | 1.3 | `text-display` |
| Heading | 20px / 1.25rem | 600 | 1.35 | `text-heading` |
| Body | 16px / 1rem | 400 | 1.5 | `text-body` |
| Label | 14px / 0.875rem | 600 | 1.4 | `text-label` |

Four sizes, two weights. Caption/muted text reuses **Label size at weight 400** rather than adding a
fifth size — differentiation comes from colour (`text-muted`), not scale.

### The 16px input floor

**Every `<input>`, `<select>`, and `<textarea>` in this project renders at ≥16px.** Below 16px,
iOS Safari zooms the viewport on focus, the layout jumps mid-entry, and the submit button is pushed
off-screen. This is a hard rule from the UX research with no exceptions.

The fix is font-size. It is **not** `maximum-scale=1` or `user-scalable=no` — those disable pinch
zoom entirely and are a WCAG failure (SC 1.4.4 Resize Text).

Enforced globally in base CSS so no component can opt out by omission:

```css
input, select, textarea { font-size: max(1rem, 16px); }
```

Phase 1 has no text inputs. The rule is declared and enforced now so Phase 3's amount field inherits
it rather than rediscovering the bug on a real phone in a restaurant.

### Money — the tabular contract

Money is **integer VND**, formatted with Vietnamese grouping (dots) and a trailing `₫`.
Verified via Node `Intl`:

```js
new Intl.NumberFormat('vi-VN').format(150000)   // → "150.000"
new Intl.NumberFormat('vi-VN').format(1234567)  // → "1.234.567"
// grouping separator confirmed as "." via formatToParts
```

`Intl.NumberFormat('vi-VN', { style: 'currency', currency: 'VND' })` also produces exactly
`150.000 ₫` (non-breaking space + ₫). Either is acceptable; prefer the explicit
`format(n) + ' ₫'` form so the separator logic is reusable by Phase 3's live-formatting amount input,
which must insert separators while the user types.

**Every rendered amount must carry the `.money` treatment:**

```css
.money {
  font-variant-numeric: tabular-nums lining-nums;
  font-feature-settings: 'tnum' 1, 'lnum' 1;  /* belt + braces for older engines */
  line-height: 1.2;                            /* permitted exception — no diacritics */
  white-space: nowrap;                         /* never break "150.000 ₫" across lines */
}
```

Rationale for each:
- `tabular-nums` — digits take equal advance width so columns align and a live-updating total does
  not shift horizontally as the user types.
- `nowrap` — a wrapped `₫` orphaned onto its own line is a recurring bug in currency UIs.
- Verified Inter exposes `tnum`; the utility is not a no-op here (it would have been with Be Vietnam Pro).

Phase 1 displays no money. The token exists so Phase 4 does not invent a second convention.

## Color

The brief asks for *trustworthy and calm*, not fintech-neon, not playful-consumer. The palette is a
**warm neutral** (`stone`) base with a **single desaturated teal** accent. Warm greys read as calmer
and less clinical than blue-greys; teal is adjacent to the "money/positive" green without being the
same hue, so the accent never competes with the balance semantics.

All ratios below are **computed**, not estimated (WCAG 2.1 relative luminance).

| Border | `--color-border` | `#E7E5E4` | 1.20 | Hairlines, dividers |

### Accent reserved for

The accent is **not** "all interactive elements". It is reserved for exactly:

1. The **primary action button** on a screen — at most one per screen. In Phase 1 that is
   *Đăng nhập với Google* (and it is a *secondary*-styled button, see below — so Phase 1 uses the
   accent only in the focus ring and the logo mark).
2. The **focus ring** on any focusable element.
3. The **active tab indicator** in the Phase 3 bottom tab bar.
4. The **FAB** (add-expense) introduced in Phase 3.
5. The **logo/wordmark** glyph.

Explicitly **not** accent-coloured: links in body copy (use `text-primary` + underline), secondary
buttons, icons, borders, hover states, headings, or any informational surface.

### Why `#059669` is dropped

The legacy Apps Script used `#059669` green and `#dc2626` red. Measured:

| Legacy colour | Contrast on `#FAFAF9` | Verdict |
|---|---|---|
| `#059669` | **3.61 : 1** | ❌ **Fails WCAG AA** for normal text (needs 4.5) |
| `#DC2626` | 4.62 : 1 | ⚠️ Passes, but with almost no margin |

`#059669` is the colour of the single most important sentence in the app — *"Bạn được nhận
80.000 ₫"* — and it is not legible to WCAG AA. On a phone screen, outdoors, at 4G-brightness, in a
restaurant, this is a real failure and not a checkbox. It is replaced with `#047857`
(emerald-700, **5.25:1**), which is the same hue family, reads as the same "green", and passes.

`#DC2626` → `#B91C1C` (**6.19:1**) for the same reason plus margin.

### Colour-blindness — the finding that changes the design

Roughly 8% of men have red-green colour vision deficiency, and in this app the red/green distinction
*is the product*. Deuteranopia and protanopia were simulated (Viénot 1999 matrices on linear RGB)
for every candidate pair:

| Pair | Normal | Deuteranopia | **Protanopia** |
|---|---|---|---|
| Legacy `#059669` / `#DC2626` | 1.28 | 3.31 | **2.19** |
| Chosen `#047857` / `#B91C1C` | ~1.2 | 3.14 | **1.92** |
| Dark `#34D399` / `#FCA5A5` | 1.45 | 2.73 | **1.25** |

All 25 AA-passing green/red combinations were searched. **The best achievable protanopic separation
was 2.49:1 — none reached 3:1.** Under protanopia, `#047857` simulates to `#70706E` and `#B91C1C`
to `#47473C`: two muddy olive-greys.

**Conclusion: hue cannot carry this meaning. This is not fixable by picking better colours.**

### Redundant encoding — mandatory, enforced

Colour is demoted to *reinforcement*. Meaning is carried by three independent channels, and the
first one alone must be sufficient:

1. **Words — the primary channel.** Never a bare signed number. Always a Vietnamese verb phrase
   with explicit direction: `Bạn đang nợ` / `Bạn được nhận`. A user who sees no colour at all reads
   the correct answer. This matches the UX research's Tier-1 recommendation (sentence first,
   number second) and is the reason that recommendation exists.
2. **Grouping and position.** The balance list is split under two headers (`Bạn nợ` / `Được nhận`)
   rather than mixing signs in one list. Direction is inferable from *which section a row is in*.
3. **Icon shape.** A directional glyph (arrow-up-right for outgoing, arrow-down-left for incoming)
   accompanies the amount. Distinguishable by shape, not fill.

Colour is the fourth channel. **Rule for every later phase: no UI element may use the
positive/negative colours as the sole differentiator.** A checker reviewing Phase 4 should fail any
balance row that is distinguished only by hue.

A `prefers-contrast: more` block additionally adds a left border to each row — shape-based, works at
any CVD.

## Dark Mode — decision: YES, ship it in Phase 1

**Decided now, deliberately, because retrofitting means touching every component.**

**Arguments for:**

- **Use context.** The primary scenario is a phone, in a restaurant, often in the evening. This is
  the canonical dark-mode environment. A full-white `#FFFFFF` screen at night is physically
  uncomfortable and makes the user the person squinting at a bright rectangle at dinner.
- **The marginal cost here is near zero, and only here.** Because every token is *semantic*
  (`--color-surface`, never `--color-stone-50`), dark mode is one additional
  `@media (prefers-color-scheme: dark)` block that reassigns ~12 variables. Components reference
  `bg-surface`; they are already theme-agnostic. The cost is one CSS block **in this phase**, versus
  auditing every screen across 8 phases later.
- **It forces token discipline immediately.** Committing to dark mode makes a raw
  `bg-white` or `text-gray-900` in any component a visible bug on day one rather than a latent one.
  This is the single most effective guard against token drift — and token drift is this document's
  whole purpose.
- **The colour work is already done.** The dark values above are measured and AA-passing. Deferring
  would discard that.

**Arguments against, and responses:**

- *"Three screens don't need it."* — True, and irrelevant. The point is the 8 phases after.
- *"Doubles visual QA surface."* — Real, but bounded: there is no third theme, and both are
  derived from one token set.

**Implementation: `prefers-color-scheme` only. No in-app toggle.**

A manual toggle requires persisted preference, a server/client hydration strategy to avoid a
flash-of-wrong-theme, and a settings UI that does not exist until Phase 5 (`Nhóm` tab). The OS
preference is correct for ~100% of a 10-person group who already set their phone to auto-dark.
A toggle is listed in Deferred below; because tokens are semantic, adding one later is a
`@custom-variant` change plus a `<html>` class — not a repaint.

```css
/* Deferred — when a manual toggle is wanted, this is the entire change: */
/* @custom-variant dark (&:where(.dark, .dark *)); */
```

`color-scheme: light dark` is set on `:root` so native form controls, scrollbars, and the
browser-chrome address bar follow the theme.

## Radii

Tailwind v4's default radius ramp is kept; we only *select* from it and bind semantic aliases.

| Token | Value | Tailwind | Usage |
|-------|-------|----------|-------|
| `--radius-control` | 8px | `rounded-lg` | Buttons, inputs, toggles |
| `--radius-card` | 12px | `rounded-xl` | Cards, raised surfaces, message panels |
| `--radius-sheet` | 16px | `rounded-2xl` | Bottom sheet top corners (Phase 3) |
| `--radius-pill` | 9999px | `rounded-full` | Avatars, badges, FAB |

**Deviation from Tailwind defaults:** none in value. Default `rounded-sm`(4px), `rounded-md`(6px),
`rounded-3xl`(24px), `rounded-4xl`(32px) remain available but are **not** part of the contract —
using them is a drift signal. The ramp is deliberately coarse: 8 / 12 / 16 / full. Four options
prevent the "every component is a slightly different roundness" failure.

Rationale for 8px controls over 6px: at 44px minimum touch height, 6px reads nearly square on a
phone; 8px is visibly soft without being a pill, which keeps the calm, non-playful register.

## Shadows

Deliberately minimal. A calm money app earns hierarchy from **surface colour and borders**, not
from elevation theatre. Heavy shadows are a primary "generic AI design" tell and read as consumer-playful.

| Token | Value | Usage |
|-------|-------|-------|
| `--shadow-card` | `0 1px 2px 0 rgb(0 0 0 / 0.04), 0 1px 3px 0 rgb(0 0 0 / 0.06)` | Raised cards |
| `--shadow-sheet` | `0 -2px 16px 0 rgb(0 0 0 / 0.10)` | Bottom sheet / tab bar (upward) |
| `--shadow-fab` | `0 2px 8px 0 rgb(0 0 0 / 0.16)` | FAB only (Phase 3) |

**In dark mode, shadows are suppressed** (`--shadow-card: none`). Shadow does not read on a near-black
surface; separation comes from `--color-surface-raised` being *lighter* than the background, which is
how depth works in dark UI. Phase 1 defines this so later phases don't stack ineffective shadows.

Phase 1 uses `--shadow-card` on at most one element. `--shadow-sheet` and `--shadow-fab` are declared
but unused — they exist so Phase 3 does not invent values.

## The Tailwind v4 `@theme` Block

Verified against the current Tailwind v4 docs (v4.3). v4 defines tokens in CSS via `@theme`;
`tailwind.config.js` is the v3 mechanism and is **not** used.

Key syntax points confirmed from the docs:
- `@theme` must be **top level** — not nested in a selector or media query.
- Tokens in a namespace (`--color-*`, `--text-*`, `--radius-*`…) generate utilities
  (`bg-surface`, `text-body`, `rounded-card`).
- `@theme inline` is required when a token **references another variable** (our `--font-sans`
  points at next/font's `--font-inter`). Without `inline`, the utility resolves to the variable
  reference and can fall back unexpectedly.
- Dark-mode overrides belong in a plain `:root`/media block, **not** inside `@theme`.

`app/globals.css`:

```css
@import "tailwindcss";

/* ---- Font family must be `inline` — it references next/font's generated variable ---- */
@theme inline {
  --font-sans: var(--font-inter), -apple-system, BlinkMacSystemFont, "Segoe UI",
               Roboto, "Helvetica Neue", Arial, "Noto Sans", sans-serif;
}

@theme {
  /* ---------- Typography ---------- */
  /* `--text-*` with a `--line-height` pair sets size + leading together */
  --text-display: 2rem;          /* 32px */
  --text-display--line-height: 1.3;
  --text-display--font-weight: 600;

  --text-heading: 1.25rem;       /* 20px */
  --text-heading--line-height: 1.35;
  --text-heading--font-weight: 600;

  --text-body: 1rem;             /* 16px */
  --text-body--line-height: 1.5;

  --text-label: 0.875rem;        /* 14px */
  --text-label--line-height: 1.4;
  --text-label--font-weight: 600;

  --font-weight-regular: 400;
  --font-weight-semibold: 600;

  /* ---------- Spacing (4px base; v4 generates all multiples) ---------- */
  --spacing: 0.25rem;

  /* ---------- Radii ---------- */
  --radius-control: 0.5rem;   /* 8px  */
  --radius-card: 0.75rem;     /* 12px */
  --radius-sheet: 1rem;       /* 16px */

  /* ---------- Shadows ---------- */

### What the shell contains in Phase 1

┌─────────────────────────────┐
│   safe-area-top             │  env(safe-area-inset-top)
├─────────────────────────────┤

**Static (no `await`, renders instantly):** the `<html>`/`<body>` chrome, theme tokens, font,

the *page*, not the layout, wrapped in `<Suspense>`. If the layout awaited the session, the entire

// app/layout.tsx — fully static, zero awaits

            className="flex h-14 shrink-0 items-center justify-between border-b border-border

            style={{ paddingTop: 'var(--shell-safe-top)' }}
          >
            <span className="text-heading text-primary">Upper-I</span>
            {/* Phase 3+: avatar / account menu mounts here */}
            <div className="min-h-[var(--size-touch-min)] min-w-[var(--size-touch-min)]" />
          </header>

          <main
            className="flex-1 px-[var(--shell-gutter)]"
            style={{
              /* Reserves space for the Phase 3 tab bar. 0px today; 56px then.
                 Nothing else changes when the tab bar lands. */
              paddingBottom:
                'calc(var(--shell-tabbar-height) + var(--shell-safe-bottom))',
            }}
          >
            {children}
          </main>

          {/* Phase 3: <BottomTabBar /> mounts here — Số dư / Lịch sử / Nhóm */}
        </div>
      </body>
    </html>
  );

```

`lang="vi"` is set so screen readers use Vietnamese pronunciation and the browser offers the correct
hyphenation/translation behaviour.

### How this anticipates the Phase 3 tab bar

Phase 1 **must not build** the tab bar. It builds the *hole* the tab bar drops into:

1. **`--shell-tabbar-height`** is already declared and already consumed by `<main>`'s bottom padding.
   Phase 3 changes `0px` → `56px` in one place; every screen's scroll bottom corrects simultaneously.
   Without this, Phase 3 would have to add bottom padding to each screen individually and would miss one.
2. **The flex column** already has a slot after `<main>`. The tab bar is `position: fixed` with
   `bottom: 0`, but the reserved padding is what keeps content from scrolling underneath it.
3. **Safe-area bottom is composed, not replaced** —
   `calc(var(--shell-tabbar-height) + var(--shell-safe-bottom))`. On a notched phone the tab bar sits
   above the home indicator and content clears both. Getting this wrong is the single most common
   iOS layout bug in bottom-tab apps.
4. **`min-h-dvh`, not `min-h-screen`.** `dvh` tracks the *dynamic* viewport as mobile browser chrome
   collapses on scroll; `vh` does not, and causes a bottom-anchored bar to drift under the URL bar.
5. **The header's right slot** is a 44×44 spacer today, so adding the avatar in Phase 3 does not
   change the header's height or shift the wordmark.

**Tab labels are fixed now** (from UX research, for Phase 3): `Số dư` · `Lịch sử` · `Nhóm`.
Three tabs, not five. The add-expense FAB is *not* a tab — it floats on every tab.

## Loading & Skeleton Conventions

Established now because every later phase needs it, and inconsistent loading treatment is the most
visible kind of drift.

### The actual latency budget

Neon free-tier compute auto-suspends when idle and resumes in **a few hundred milliseconds**. This
is the defining number. PROJECT.md explicitly notes resume is fast enough that no
avoidance architecture is needed.

Research-backed perception thresholds:

| Duration | Perception | Correct treatment |
|---|---|---|
| < 100ms | Instantaneous | Nothing. A spinner here *adds* perceived latency |
| 100–300ms | Barely noticed | Nothing. This is the common Neon-resume case |
| 300ms–1s | Noticeable | Skeleton matching final layout |
| > 1s | Attention wanders | Skeleton + (after 3s) a reassuring message |

### The rules

**Rule 1 — The shell never loads.** It is static. The user always sees the header, background, and
layout within one paint. This alone covers most of the Neon resume window: by the time compute is
awake, the app already looked alive.

**Rule 2 — Skeletons, not spinners, for content.** A spinner communicates "something is happening";
a skeleton communicates "*this specific thing* is arriving" and prevents the layout shift that
occurs when content replaces a centred spinner. Spinners are permitted **only** inside a button
that the user just pressed (see Rule 5).

**Rule 3 — Skeletons must match the final layout's box.** Same height, same width, same radius, same
position. A skeleton of the wrong size is worse than none because it guarantees a visible jump
(and a CLS penalty).

**Rule 4 — Delay the skeleton by 150ms.** Content that arrives in 120ms should never flash a
skeleton; a skeleton appearing and vanishing within one frame reads as a glitch. Implemented in CSS
so it costs no JS:

```css
.skeleton {
  background-color: var(--color-surface-sunken);
  border-radius: var(--radius-control);
  animation: var(--animate-skeleton);
  animation-delay: 150ms;
  opacity: 0;
  animation-fill-mode: forwards;
}
```

**Rule 5 — Action feedback is immediate and in-place.** When the user taps a button, that button
enters a pending state *on the same frame*: `aria-busy="true"`, `disabled`, label swapped to the
progressive form, inline spinner. Never a full-page overlay. The button must **not change width**
when its label changes, or the layout jumps under the user's thumb.

**Rule 6 — Opacity pulse, not shimmer sweep.** A translating gradient costs a repaint on a low-end
Android phone on 4G. `opacity` is compositor-only. It is also calmer, which fits the register.

**Rule 7 — Respect `prefers-reduced-motion`.** The global reduce block already freezes the pulse to
a static tint. A pulsing rectangle is a vestibular trigger.

### Phase 1 application

Phase 1 has exactly one suspendable boundary: the authenticated page's user name.

```tsx
// app/(app)/page.tsx
<Suspense fallback={<div className="skeleton h-7 w-48" />}>
  <UserGreeting />
</Suspense>
```

`h-7` (28px) and `w-48` match the rendered greeting's box, so there is no shift when the name lands.
This one-line pattern is the template for Phase 4's balance card and Phase 7's history list.

## Focus & Accessibility Baseline

**Target: WCAG 2.1 Level AA.** Every colour pair in this document is measured against it above.

### Focus ring

| Property | Value | Why |
|---|---|---|
| Style | `2px solid var(--color-focus)` | 2px is visible on a phone; 1px disappears at high DPI |
| Offset | `outline-offset: 2px` | Ring sits *outside* the element so it never obscures the label |
| Trigger | `:focus-visible` | Keyboard/AT only — no ring on mouse/touch tap, which users read as a stuck state |
| Contrast | 5.24:1 light / 10.61:1 dark vs surface | Exceeds the 3:1 required for non-text UI (SC 1.4.11) |

**`outline: none` is banned.** There is no case in this project where removing the focus indicator
is correct. If a ring looks wrong, change the offset or radius.

Because the ring is drawn on the token `--color-focus`, it automatically has adequate contrast in
both themes — which is precisely the kind of thing that breaks when dark mode is retrofitted.

### The Google sign-in button and keyboard navigation

This is the only interactive element on the app's entry screen, so its keyboard behaviour is the
whole keyboard story of Phase 1.

| Requirement | Implementation |
|---|---|
| Natively focusable | A real `<button type="submit">` inside a `<form>`. **Not** a `<div onClick>` — a div has no tab stop, no Enter/Space activation, and no implicit `button` role |
| First tab stop | It is the only focusable element on the page; no skip-link needed for a single-control screen |
| Activates on **Enter** and **Space** | Free with a native `<button>`. A div would need both handlers plus `role` plus `tabIndex` — three chances to get it wrong |
| Visible focus | Inherits the global `:focus-visible` ring; `outline-offset: 2px` clears the button's 8px radius |
| Touch target | `min-height: 44px` — in practice 48px for comfort |
| Accessible name | Text content `Đăng nhập với Google` is the name. The Google `<svg>` is `aria-hidden="true"` + `focusable="false"` so AT doesn't announce a decorative graphic |
| Pending state | On submit: `disabled` + `aria-busy="true"`, label → `Đang chuyển tới Google…`. Width is fixed so no reflow |
| Double-submit | `disabled` on first submit prevents a second OAuth round-trip on a flaky 4G double-tap |
| Server action | Form posts to a server action, so it **works before hydration** — important on 4G where JS may still be loading |

```tsx
<form action={signInWithGoogle}>
  <button
    type="submit"
    className="flex min-h-12 w-full items-center justify-center gap-3
               rounded-control border border-border-strong bg-surface-raised
               px-6 text-body font-semibold text-text-primary
               transition-colors hover:bg-surface-sunken
               disabled:opacity-60"
  >
    <GoogleMark aria-hidden="true" focusable="false" className="size-5" />
    Đăng nhập với Google
  </button>
</form>
```

### Baseline rules for all phases

1. **Contrast:** text ≥ 4.5:1; large text (≥24px or ≥19px bold) ≥ 3:1; UI boundaries ≥ 3:1. Every
   token above is measured and recorded, so a later phase can check without recomputing.
2. **Touch targets:** ≥ 44×44px with ≥ 8px spacing between adjacent targets.
3. **Semantic HTML first:** `<button>` for actions, `<a>` for navigation, one `<h1>` per page,
   landmarks (`<header>`/`<main>`/`<nav>`) present.
4. **`lang="vi"`** on `<html>` — drives screen-reader pronunciation of Vietnamese.
5. **Colour is never the only channel** — see the redundant-encoding contract. This is the single
   most consequential a11y rule in this project and it binds every later phase.
6. **Zoom to 200% must not break layout** (SC 1.4.4) — guaranteed by `rem` sizing and no
   `user-scalable=no`.
7. **`prefers-reduced-motion`** honoured globally.

**Tone — the hard part.** The brief requires clarity that the email is not invited, *without*

- **A next step is given.** "nhắn cho người quản lý nhóm để được thêm vào" — there *is* a path

**What this screen deliberately does not have:** no balance, no money, no navigation, no tab bar, no
FAB, no settings. CONTEXT.md forbids any transaction-related surface in Phase 1.

**What it proves about the token system** — this is the 70% payoff, visible on a real phone:

| Token exercised | Via |
|---|---|
| `--text-display` + Vietnamese line-height | `Chào {name}` — a name with diacritics (`Chào`, `Mạnh`, `Hồng`) is the live test that 1.3 leading doesn't clip |
| `--text-body`, `--text-label` | Card body, email line |
| `--color-surface` vs `--color-surface-raised` | Page background vs card — the separation that must survive dark mode |
| `--color-text-primary/secondary/muted` | All three rendered side by side |
| `--radius-card`, `--shadow-card` | The card |
| Dark mode | Flipping the OS theme re-skins the whole screen with no component change — **this is the proof that dark mode was worth deciding now** |
| Safe-area insets | Visible on a notched phone: content clears the notch and home indicator |
| Focus ring | Tab to the sign-out button |
| `--size-touch-min` | Sign-out button height |

| Element | Copy (Vietnamese) |
|---|---|
| Greeting | `Chào {displayName}` |
| Identity | `{email}` |
| Card body | `Nhóm đã sẵn sàng. Tính năng ghi chi tiêu sẽ có ở bản cập nhật tiếp theo.` |

`error` if the session query fails; **no empty state** — an authenticated user always has a name,

## Copywriting Contract

Vietnamese copy principles, binding on all phases:

1. **Second person, informal-neutral: `bạn`.** Ten friends; `quý khách` would be absurd.
2. **Verb phrases with direction, never bare signed numbers.** `Bạn đang nợ 150.000 ₫`, never
   `−150.000 ₫`. This is the primary carrier of owe/owed meaning and the reason the app is usable
   without colour vision.
3. **Errors state the problem and the next step.** Never a bare `Đã có lỗi xảy ra`.
4. **No jargon:** no `số dư ròng`, no `bút toán`, no `ledger` in user-facing copy. The research is
   explicit that users confuse "balance" with "what I pay now".
5. **Sentence case.** Vietnamese does not use title case; capitalised headings look like shouting.
6. **Buttons are verbs.** `Đăng nhập với Google`, `Thử lại`, `Đăng xuất` — never `OK` / `Submit`.

| Element | Copy |
|---------|------|
| Primary CTA (Phase 1) | `Đăng nhập với Google` |
| Secondary action | `Dùng tài khoản khác` |
| Sign out | `Đăng xuất` |
| Empty state heading | *Not applicable in Phase 1* — no list surface exists |
| Empty state body | *Not applicable in Phase 1* |
| Error state — OAuth | `Đăng nhập không thành công` / `Có lỗi khi kết nối với Google. Kiểm tra kết nối mạng rồi thử lại.` → `Thử lại` |
| Error state — network | `Mất kết nối` / `Không kết nối được máy chủ. Kiểm tra mạng rồi thử lại.` → `Thử lại` |
| Error state — session | `Không tải được thông tin` / `Không lấy được thông tin tài khoản. Kéo xuống để tải lại.` → `Tải lại` |
| Not-invited (not an error) | `Email này chưa được mời` / `Tài khoản {email} chưa có trong danh sách thành viên của nhóm.` |
| Destructive confirmation | **None in Phase 1.** No destructive action exists — sign-out is reversible by signing in again, so it gets no confirmation dialog. Phase 4's reversing-entry is the first true destructive action and must define its own |

### Reserved vocabulary (locked now, used from Phase 4)

Fixing these in Phase 1 prevents three phases from inventing three synonyms for the same concept:

| Concept | Vietnamese | Never |
|---|---|---|
| You owe | `Bạn đang nợ` | `số dư âm`, `−150.000` |
| You are owed | `Bạn được nhận` | `số dư dương` |
| Per-person section headers | `Bạn nợ` / `Được nhận` | mixed signed list |
| Pay now | `Trả ngay` | `Thanh toán`, `Settle` |
| Remind | `Nhắc` | `Đòi` |
| Add expense | `Thêm chi tiêu` | `Tạo giao dịch` |
| Tabs | `Số dư` · `Lịch sử` · `Nhóm` | `Trang chủ`, `Cài đặt` |

## Contract Rules for Later Phases

The clauses below are the durable output of this phase. A checker auditing Phases 2–9 should treat
each as a pass/fail gate.

1. **Never use a raw Tailwind palette colour.** No `bg-white`, `text-gray-900`, `border-stone-200`.
   Only semantic tokens. A raw colour is a dark-mode bug that will not be visible in light mode.
2. **Colour is never the sole carrier of owe/owed meaning.** Words first, then grouping, then icon
   shape, then colour. Protanopic separation is 1.92:1 — hue genuinely does not work.
3. **Never `leading-tight`/`leading-none` on Vietnamese prose.** Minimum 1.3; measured ink span is
   1.321em.
4. **Every input ≥ 16px.** Enforced in base CSS; do not override.
5. **Every amount uses `.money`.** Tabular, nowrap.
6. **Every touch target ≥ 44×44px** with ≥ 8px gaps.
7. **Never `outline: none`.**
8. **Bottom-anchored UI composes `--shell-tabbar-height` with `--shell-safe-bottom`.**
9. **The root layout performs no `await`.** INFRA-07 depends on it.
10. **Two font weights only: 400 and 600.**
11. **Four type sizes only.** New emphasis comes from weight or colour, not a new size.
12. **Four radii only:** 8 / 12 / 16 / full.
